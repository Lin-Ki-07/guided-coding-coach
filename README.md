## 适合谁

你已经有一个项目，想继续完善它，也希望逐渐拥有独立修改、排错和解释设计的能力。

也许你经常遇到这些问题：

- 能看懂单个函数，却串不起来整个项目的执行过程。
- 收到一大段修改建议，仍然不知道代码放在哪、旧代码删多少。
- 跟着教程跑通了，回头却说不清为什么要引入这些类和模块。
- 想把每一步整理成清晰的提交，并在换对话或面试时讲明白。

**guided-coding-coach 把这些需求组织成一套可复用的教学协作流程。** 默认由你修改功能代码，助手负责解释、定位、审查和验证建议；你也可以明确要求助手直接实现。

## 看个例子

下面是一段教学方式示意；真实建议需要先检查你的代码。

> **你：** 我已经把执行循环移进 `ReActAgent` 类了，下一步呢？
>
> **助手：** 先检查这次迁移是否完整。如果源码确认循环已经迁移，接下来按这份清单推进：
>
> 阶段一：让 Agent 使用自己的配置；完成后不同实例可以独立运行。
>
> - 1.1 [当前] 运行方法读取实例提示词；验收：调用模型时收到该实例的提示词。
> - 1.2 [待开始] 核对配置隔离；验收：两个实例使用不同配置时互不影响。
>
> 阶段二：整理迁移结果；完成后能够复现并解释当前版本。
>
> - 2.1 [待开始] 更新运行说明；验收：说明中的入口和配置用法与源码一致。
>
> 现在展开 1.1：“让实例使用自己的提示词”。
>
> 例如，初始化时保存的 `self.system_prompt` 是这一个 Agent 的提示词。运行方法如果仍读取全局变量，创建第二个 Agent 时就无法可靠地使用不同配置。
>
> 在你的项目里，助手会指出实际文件、方法及需要替换的语句，并解释相关调用处是否也要修改。
>
> 修改后，先检查导入和语法，再分别验证不同实例能否使用各自的提示词。需要真实模型调用的验证会单独说明。
>
> 检查通过后，提交建议：`refactor: 使用 Agent 实例保存的提示词`。

每一步都围绕三个问题展开：**为什么改、具体怎么改、如何知道改对了。**

## 如何陪你写代码

```text
读取当前代码与已有计划
          ↓
展示阶段与编号小目标、验收标准和进度
          ↓
展开当前一个可验证的小目标
          ↓
解释原理，明确修改位置
          ↓
       你来修改
          ↓
   审查改动与验证结果
          ↓
整理 commit 建议，进入下一步
```

| 环节 | 你会得到什么 |
| --- | --- |
| 接手项目 | 基于实际代码确认进度，区分已实现、已验证和暂缓事项 |
| 规划全貌 | 列出各阶段的小目标与验收标准，标明当前步骤和后续顺序 |
| 解释修改 | 把概念对应到当前代码的输入、输出、调用关系和职责 |
| 指导动手 | 指明文件、类或函数，以及新增、替换或删除的范围 |
| 检查排错 | 优先解决阻塞问题，区分行为错误与可选改进 |
| 验证提交 | 给出预期现象、验证边界和匹配变更的 commit 信息 |
| 阶段复盘 | 整理版本说明、架构流程、交接材料与面试讲解要点 |

## 安装

将本仓库下载或克隆到本地，再把包含 `SKILL.md` 的整个 `guided-coding-coach` 文件夹放入 Codex 的个人 skills 目录。

默认目录结构：

```text
~/.codex/skills/
└── guided-coding-coach/
    ├── SKILL.md
    ├── README.md
    └── LICENSE
```

- Windows：用户目录下的 `.codex\skills`。
- macOS / Linux：`~/.codex/skills`。
- 设置了 `CODEX_HOME` 时：使用其下的 `skills` 目录。

已有同名技能时，先比较内容再决定是否替换。安装后在新对话中检查技能是否可用。

## 开始使用

打开你的项目，在 Codex 对话中明确调用：

```text
使用 $guided-coding-coach。
先检查当前项目，告诉我它现在如何运行。针对本次改进目标，
先列出各阶段下的编号小目标、验收标准与当前进度，再带我完成第一步。
功能代码由我修改，请解释原因、明确修改位置，并给出验证方法。
```

## 协作约定

**先看全貌，再小步推进。** 多步骤任务先展示“阶段 → 编号小目标 → 验收标准”的完整清单，标明当前和后续步骤。每轮只展开当前小目标，检查后更新进度；计划调整时说明原因。

**说明具体位置。** 结合实际代码说明改哪个文件、哪个方法、保留什么、替换什么。必要代码不靠省略号猜测。

**理解优先。** 解释为什么引入抽象或框架，以及它解决了当前什么问题；不预设你的语言、框架或架构偏好。

**结果有边界。** 语法检查通过、一次运行成功和完整功能验证是不同结论。复盘时也会区分自己实现的部分与依赖库提供的能力。

**授权跟随当前要求。** 默认由学习者动手；明确要求助手实现时按授权范围执行。commit 建议本身不代表允许自动提交、推送、合并或发布。

## 贡献

欢迎通过 Issue 或 Pull Request 提出改进。最有帮助的反馈是：

1. 你希望学习或完成什么。
2. 助手在哪一步没讲清楚、推进过快或误解了当前状态。
3. 你希望它如何调整。

示例请尽量简短，并移除密钥、私人聊天记录和未获授权的项目代码。

本仓库仅包含指令文档，没有运行时程序或自动化测试套件。格式检查不能证明教学效果；欢迎用具体使用案例帮助改进。
